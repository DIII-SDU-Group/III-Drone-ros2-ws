# Standalone GC installation and III runtime routing

Status: **Ready for execution in dependency order.** Planning only. The original request is reproduced verbatim in the appendix for final execution review. This backlog does not perform installation or runtime work.

## Outcome and scope

Install the workstation or ground computer operator stack from one standalone repository script, with `dev` and `deploy` installation profiles. The installation verifies prerequisites, installs GUI v2, a checkout-pinned QGroundControl asset, and the checkout's III CLI as a native host command. It provides deterministic paths for the existing SIM and HIL launchers and for real/OptiTrack ground-computer operation. Runtime management belongs to `iii`: local on the devcontainer/Pi, remote from the native workstation/ground computer. `iii-dev` retains simulation and host-container orchestration only where it adds work outside the ordinary CLI.

This is a developer workflow over the editable checkout. It must preserve the active safety boundaries in `AGENTS.md` §7.2: do not arm, write PX4 firmware/parameters, compile on the Pi, add release security machinery, or erase unrelated dirty state. Planning and routine unit tests do not start live runtime, QGC, or deployment; execution acceptance must still exercise installed components on available owned hosts before claiming they work there.

## Design contract and routing matrix

The following implementation contract follows the original request. The installed host `iii` is native Python in an isolated native installation, linked into a stable user PATH; no ROS/DDS is required on the GC host. Installed GC UI may use the existing Docker Compose build, but the installed launcher must operate from an installed content snapshot without relying on the checkout remaining in place. `dev` selects workstation prerequisites and allows SIM/HIL; `deploy` selects GC-computer prerequisites and allows real/OptiTrack. Both install the same checkout-pinned QGC artifact and III CLI source revision on Linux x86_64. The user confirmed the field ground computer is Linux x86_64.

| Invocation context | SIM | HIL | OptiTrack / real |
| --- | --- | --- | --- |
| Workstation native, `dev` install | `iii` routes runtime command into the checkout-matched devcontainer, no implicit local daemon | `iii` routes runtime command over SSH to selected Pi, preserving HIL profile | Outside install profile; reject |
| Workstation devcontainer | `iii` acts on local supervised SIM runtime | Outside local runtime role; reject implicit routing | Outside local runtime role; reject implicit routing |
| Pi shell | Outside local runtime role; reject implicit routing | `iii` acts on local HIL runtime | `iii` acts on local selected OptiTrack/real runtime |
| Ground computer native, `deploy` install | Outside install profile; reject | Outside install profile; reject | `iii` routes runtime command over SSH to selected Pi |

The host install profile limits allowed targets; an explicit per-command runtime target or named shell profile chooses one, with no implicit last-used vehicle. Missing or conflicting targets fail closed. Target host, runtime profile, checkout identity and route are observable in dry-run/status output. SSH must invoke the checkout-aligned Pi CLI in local mode with safely encoded arguments, preserve exit code/stdout/stderr/TTY and universal JSON results, and never recurse through a remote profile. Native SIM routing discovers only the devcontainer labeled for this checkout. Route `iii system`, `iii mission`, SIM-specific `iii config sim`, and new recorder/runtime-API service controls to the selected runtime host; keep `deploy`, `host`, PX4 inspection and host QGC/UI lifecycle in their existing host domains. The runtime host may use its local Runtime API for mission actions. GUI proxy and HIL coordinator continue using their direct Runtime API contract. This command boundary and safe target selection are supported by the original request and current code, so they do not need separate user decisions.
